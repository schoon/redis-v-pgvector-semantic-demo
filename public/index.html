redis vs pgvector

Semantic Search & Routing

Side-by-side vector search, hybrid semantic search, and semantic intent routing — Redis (RedisVL) vs Postgres (pgvector) — over a fictitious bank's customer identity operations: the requests that keep customer identity records accurate and compliant, the procedures case workers follow, and a knowledge base of SOP articles. Same corpus, same embeddings, same questions.

Vector search

Exact (FLAT/KNN) and approximate (HNSW) nearest-neighbor search over 40,000 embedded identity-ops requests.

Semantic search

Natural-language search over the procedure catalog and SOP articles, combined with category/SLA filters in one query.

Semantic caching

RedisVL's SemanticCache vs Postgres, which has no caching layer and recomputes every single call.

Semantic routing

RedisVL's built-in SemanticRouter vs a hand-rolled pgvector equivalent — routes straight into the matching search.

No real customer or case data of any kind. See Methodology.

Semantic caching, with RedisVL

One extension call checks the cache; one call populates it. No hand-rolled similarity math.

1. Customer question"what's the process for a duplicate TIN case"
↓ embed locally (sentence-transformers, no API call)
2. cache.check(vector=vec)RedisVL SemanticCache — one indexed range query against previously-answered questions
↓
HIT — distance ≤ thresholdReturn the cached response. req_flat_idx is never touched.
MISSRun the real search, then cache.store(...) for next time
from redisvl.extensions.llmcache import SemanticCache

cache = SemanticCache(
    name="req_search_cache",
    distance_threshold=0.15,
    vectorizer=my_vectorizer,
    redis_client=client,
)

def answer(query_text):
    vec = embed(query_text)
    hits = cache.check(vector=vec)
    if hits:
        return hits[0]["response"]        # cache hit — done, no search
    response = run_real_search(vec)       # cache miss — compute it once
    cache.store(prompt=query_text, response=response, vector=vec)
    return response

That's the whole implementation — no reference cosine-distance math, no manual index management. Postgres has no equivalent primitive to call here, which is the point: this is a capability, not just a faster query.

Semantic routing, with RedisVL

One extension call classifies the intent. The application reuses that same vector to act on it.

1. Customer question"I think two of my accounts share the same SSN"
↓ embed locally (same model as everything else in this demo)
2. router(vector=vec)RedisVL SemanticRouter — compares against every route's reference utterances, averages distance per route, picks the closest one under its own threshold
↓
3. Matched route: duplicate_tin_resolution(or "no confident match" if nothing clears its threshold)
↓ reuse the SAME vector — no second embed() call
4. Act on the routeSearch the matching corpus (procedure catalog / SOP articles), or hand off to a live case-system lookup for intents like "case status" that no static corpus can answer
from redisvl.extensions.router import SemanticRouter, Route

router = SemanticRouter(
    name="intent_router",
    routes=[
        Route(name="duplicate_tin_resolution", references=[...], distance_threshold=0.5),
        Route(name="procedure_lookup", references=[...]),
        # ... 10 more intents, same shape
    ],
    vectorizer=my_vectorizer,
    redis_client=client,
)

def route_and_answer(query_text):
    vec = embed(query_text)
    match = router(vector=vec)              # one call classifies the intent
    if match.name == "procedure_lookup":
        return search_procedures(vector=vec)  # reuse the SAME vector
    elif match.name == "address_update":
        return search_sop(vector=vec)
    # ...

Postgres's equivalent (see the demo) is a hand-written SQL CTE that replicates this same two-stage filter by hand — it works, but every route-matching rule lives in application SQL instead of a three-line extension call.
