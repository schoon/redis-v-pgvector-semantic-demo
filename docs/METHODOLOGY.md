# Methodology

Read this before presenting. It covers what's fictitious, how the
comparison stays fair, two real bugs found while building this (both
about HNSW, both fixed), and what this demo does not support.

## No real customer data anywhere

Every customer, card, transaction, merchant, and support article in this
repo is synthetic, generated by `src/generate.py` from a fixed seed. The
credit-card products and their marketing copy, the FAQ articles, and the
semantic-routing intents and example utterances in `src/routes.py` are
all invented for this demo. Nothing here is drawn from or resembles a
real institution's data, a real customer's data, or a real conversation.

## Both engines answer the same question

Every comparison in this repo runs the identical query text through the
identical embedding model (`src/embeddings.py`) and passes the identical
vector to both engines. Concretely:

- **Vector search (exact/FLAT):** RedisVL's FLAT algorithm vs a Postgres
  sequential scan (HNSW index scans disabled for that one query via
  `SET LOCAL enable_indexscan/enable_bitmapscan = off`) — both compare
  every candidate, no approximation, on either side.
- **Vector search (HNSW):** an HNSW graph index on both engines, built
  with comparable parameters (see "Two real bugs" below).
- **Semantic search:** a vector search combined with TAG/NUMERIC filters
  in one query on both engines, not vector search followed by a
  separate filter step.
- **Semantic routing:** the identical two-stage classification algorithm
  on both engines (see below) — RedisVL's built-in `SemanticRouter` vs
  hand-written SQL that replicates its exact math, not an approximation
  of it.

## Scale: a laptop-sized corpus, not a claim about real data volume

5,000 customers, ~7,500 cards, 300,000 transactions (a 40,000-row sample
embedded and searched — see below), 15 card products, 26 FAQ articles,
12 routing intents with 8-15 example utterances each. Sized to run
comfortably on a MacBook, not a statement about how large a real
deployment's data is.

**Only a 40,000-row sample of transactions is embedded and searched.**
Embedding all 300,000 rows works fine locally too, but a sample is
enough to show the comparison honestly and keeps `seed_redis.py`/
`seed_pg.py` fast to re-run. `TRANSACTION_EMBED_SAMPLE` in `config.py`
controls this.

**Customer and card data is generated but not loaded into either
engine.** None of the four comparison scenarios (vector search, semantic
search, semantic routing, throughput) filters by customer — they're all
"search within the whole corpus," not "search within what one customer
can see." `customers.jsonl`/`cards.jsonl` exist so the corpus reads as a
real credit-card company's data shape, but there's nothing for either
store to join against them for right now. See "What this demo does not
support" below.

## Two real bugs, both about HNSW, both fixed

### Bug 1: building the HNSW index before the bulk load produces a worse graph

The natural-seeming order — create all indexes first, then load data —
works fine for FLAT (order-independent, it's brute force) but measurably
hurt HNSW. `redis_store.create_indexes()` used to create `tx_hnsw_idx`
up front, the same as the other three indexes, and RediSearch built the
HNSW graph incrementally as each of the 40,000 documents was `HSET` one
at a time (RediSearch's real-time on-write indexing path).

Measured directly: querying `"coffee purchase"` (a plain-language query
with no exact match anywhere in the corpus) against that index returned
"Online Shopping" transactions at a much worse (higher) distance than
the true nearest cluster. The FLAT index, same data, same query, correctly
returned "Coffee Shops." Raising `ef_runtime`/`m`/`ef_construction` on
the *incrementally-built* index didn't fix it — even `ef_runtime=400`
still returned "Online Shopping."

Dropping the index and recreating it against the *same, already-loaded*
data — triggering RediSearch's background bulk-scan indexing path
instead of the real-time on-write path — fixed it immediately, at the
same parameters that had just failed. This is why
`redis_store.create_hnsw_index()` is a separate function called only
after `load_transactions()` returns in `seed_redis.py`, and why it waits
on `FT.INFO`'s `percent_indexed` reaching `1.0` before returning (the
bulk scan is asynchronous — querying before it finishes hits a
partially-built graph, a different way to get the same kind of degraded
result). This mirrors pgvector's own documented advice to build an HNSW
index after the bulk load, not before — the Postgres side of this repo
already did that from the start.

### Bug 2: RedisVL's default `ef_runtime` (10) is too low for this corpus

Independent of build order, `ef_runtime` — the query-time candidate-list
size, trading recall for latency — defaults to 10 in RedisVL's
`HNSWVectorFieldAttributes`. Even against a correctly bulk-built index,
this occasionally missed a large, well-separated cluster for a query
with no exact match. Raised to 40 in `redis_store.py`'s
`HNSW_EF_RUNTIME`, matching `pg_store.py`'s `HNSW_EF_SEARCH = 40` — the
same value on both engines on purpose, so the comparison is "both
engines correctly configured," not "Redis tuned up, Postgres left at a
default" (or the reverse).

**Recall numbers on the HNSW tab can still look lower than expected
even when the result is correct.** Many transactions share literally
identical description text (and so identical embeddings) — "the same 8
transaction IDs as the exact search" is ambiguous whenever more than 8
rows tie at the 8th-smallest distance. The UI's "recall@8 vs exact"
figure compares specific transaction IDs, so it can read low even when
every returned transaction is the correct category at the correct
distance. `validate.py` checks this correctly (by distance value against
a tie-aware threshold — see `is_valid_top_k()`), which is why it passes
cleanly even when the UI's simpler ID-overlap number doesn't look
perfect.

## Semantic routing: the same algorithm, not two similar ones

RedisVL's `SemanticRouter` classifies a sentence by:

1. Computing distance from the query vector to every route's reference
   utterances, but **discarding any reference farther than the largest
   `distance_threshold` across all routes** before aggregating.
2. Averaging the surviving distances per route (`aggregation_method:
   avg`, the default) — a route with zero surviving references can't
   win, no matter how close its other references are.
3. Taking the lowest average, but only accepting it if that average is
   still under *that route's own* threshold.

`pg_store.route_query()` replicates all three steps in SQL — a CTE that
filters by the global max threshold before the `AVG(...)` in step 2, and
an application-level check against the winning route's own threshold in
step 3. An earlier version skipped step 1 (averaged over every
reference, unconditionally) and could pick a different winner than
RedisVL for the same sentence — a real behavioral difference, not just
an implementation detail. Verified directly: for five varied test
sentences, both engines return the same route with a distance matching
to 6 decimal places.

**Postgres wins on routing at this corpus's scale (87 reference
utterances).** RedisVL's `SemanticRouter` runs an `FT.AGGREGATE` with a
range query and a `GROUPBY`/reducer pipeline — general-purpose machinery
built to stay fast as the reference set grows into the thousands. A
hand-written `SELECT ... GROUP BY` over 87 rows in Postgres has less
overhead to amortize at this size. This is a genuine, measured result,
not a bug — see the README for the numbers, and don't be surprised if a
much larger route/reference set changes which engine wins.

## How timing works

Every comparison endpoint in `server.py` runs each engine `runs` times
(default 3, adjustable in the UI) and reports the **median**, not the
mean — one slow first-call outlier shouldn't move the number, and a
median is harder to accidentally cherry-pick than "best of N."

## What this demo does not support

- **No per-customer entitlement scoping.** Every search scenario
  searches the whole corpus. If a future version needs "search only
  within what this customer/advisor can see," look at the sibling
  `redis-v-oracle-entitlements-demo` for that pattern — it's a
  genuinely different problem (filtering by a precomputed access scope)
  from what this repo demonstrates.
- **No semantic caching.** RedisVL has a semantic cache extension; this
  demo doesn't use it, since the ask was vector search, semantic search,
  and semantic routing specifically.
- **No re-ranking.** Results are ordered by vector distance (or, for
  routing, average vector distance) only — no cross-encoder or LLM
  re-ranking step on top.
- **HNSW parameters are reasonable defaults, not tuned for this exact
  corpus.** `m=16, ef_construction=200, ef_runtime=40` (Redis) and
  `m=16, ef_construction=64, ef_search=40` (Postgres) are sensible
  starting points, chosen to be comparable to each other — not the
  result of a recall/latency sweep on this specific 40,000-row sample.
  A real tuning exercise would look different at real data volume.

## Numbers drift when the generator changes

`src/generate.py` runs off a fixed seed (`SEED` in `config.py`), so the
corpus is reproducible run to run — but changing `CATEGORIES`,
`CARD_PRODUCT_CATALOG`, `FAQ_CATALOG`, or the scale constants will
change the generated data, which will change measured latencies and
possibly which engine wins a given scenario. Re-run `validate.py` and
`bench.py` after any such change, and update the README's numbers rather
than leaving stale ones in place.
